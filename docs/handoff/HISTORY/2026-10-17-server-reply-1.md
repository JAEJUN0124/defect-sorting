# 서버 회신 반영, 실제 서버 시험, 서버 답장 준비

## 요약
- 서버 담당의 회신(받은 파일 hmi-server-reply-1-1.md, 사본 docs/hmi-server-reply-1.md)을 받았다. 서버는 1차로 `Home`에 원점 각도(`Motors`)를 받아 검사하고 `EmergencyStopRelease`를 받게 고쳤다. `ProgramStop`은 컨베이어·로봇팔 정지 요청이고 HMI 화면 종료가 아니라고 답했다. 라인 상태·이벤트·상태에 따른 거절은 2차(시뮬레이션부터), 실제 장비 연결은 3차에 하기로 했다.
- 회신과 실제 서버 주소를 받아 CURRENT의 차단 두 개(실제 서버에 붙여 보지 못함, 회신을 기다리며 서버 쪽 작업을 멈춤)와 공백 두 개(서버 담당의 답을 받지 못함, 일반 정지 필요 여부)가 풀렸다. 답이 아직 정해지지 않은 것(그리퍼 단위, 자동 작업의 원점 사용, 외부 접속)은 CURRENT 공백에 남겼다.
- 회신에 맞춰 HMI를 고쳤다: 프로그램 종료는 HMI만 닫고 서버에 보내지 않음(D-015), 정지 키는 `Stop` 대신 `ProgramStop`, 거절 Reply는 id로 찾고 답에 있는 값만 비교(`command`가 없으면 보낸 명령 이름으로 문구), 다시 붙으면 이벤트 순번을 잊음(서버가 다시 켜지면 `seq`가 1부터), 원점 복귀는 원점 각도를 싣는 것이 기본.
- 사용자가 준 실제 서버 주소(`ws://10.108.108.98:5080/ws/hmi`)로 요청을 다섯 번 보냈다: 요청 31개 두 번, 값을 넣은 16개, 큰 값 15개를 한꺼번에, 긴급정지 16개(한 번, id가 다른 10개, id가 같은 5개). 모든 요청에 5~25ms 안에 답이 왔고 연결은 끝까지 유지됐다. 정상 명령은 모두 받음 확인(`Received`·`ReceiptOnly`, `executed="false"`)이었다. 결과 표는 docs/hmi-server-answer-1.md 6장.
- 큰 값 시험 직후 서버 담당이 상태 전송 간격을 1초에서 60초로 바꿨다. 그러자 HMI가 약 4초마다 "연결 끊김"을 띄우고 다시 붙었다. 연결 확인을 상태 받기와 나눠, 60초마다 `Ping`을 보내고 65초 넘게 아무 메시지가 없으면 끊김으로 보며, 상태는 60초 넘게 오지 않을 때만 `GetStatus`로 묻게 고쳤다. 60초는 사용자가 정했다.
- 회신에 대한 답장(docs/hmi-server-answer-1.md)을 썼다. 서버 쪽에 부탁하는 것은 0장에 모아, 서버 담당이 AI에 그대로 넘겨도 되게 했다(0.1 메인 서버에서 HMI 화면 띄우기, 0.2 보내 주실 것, 0.3 같이 정할 것, 0.4 2차 모양, 0.5 하지 않아도 되는 것). 사용자가 보내기를 멈춰 아직 보내지 않았다.

## 시도했다가 버린 방법
- 상태가 3초 넘게 오지 않으면 끊김으로 보기 → 서버가 상태 간격을 60초로 바꾸자 약 4초마다 끊김과 다시 붙기가 생김 (직접 2026-10-16 · 실제 서버) → 연결 확인은 `Ping`/`Pong`으로 따로 하고 상태는 드물게 묻기
- 연결 확인 `Ping`을 1초마다 보내기 → 사용자가 60초마다로 하라고 함 (사용자 2026-10-16) → 60초마다, 끊김 판단은 65초(설정을 Ping 간격 + 5초보다 짧게 해도 그 값으로 씀)
