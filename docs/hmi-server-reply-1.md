# HMI 서버 연동 요청 회신 초안

- 작성일: 2026-10-14
- 반영 확인일: 2026-10-16
- 보내는 쪽: 서버 담당
- 받는 쪽: HMI 담당
- 대상: `hmi-server-requests-1.md`, XML 규약 v1.0 후속 요청
- 상태: Home 각도 수신·검증과 EmergencyStopRelease 수신은 승인 후 코드·README에 반영했습니다. 실제 장비 제어 및 그 밖의 확장은 협의안이며 외부 HMI에 배포·연동한 상태는 아닙니다.

요청 내용 확인했습니다. 제안하신 XML 구조는 대부분 서버에서 확장할 수 있습니다. 다만 현재 서버는 장비와 연결되어 있지 않고 명령 수신 확인까지만 수행합니다. 수신 확인, 실행 시작, 동작 완료를 구분하여 연동하고자 합니다.

우선 `ProgramStop`의 의미와 종료 화면 전환 조건을 맞춰야 합니다. 원점 각도 전달, 라인 상태, 긴급정지 해제, 이벤트는 아래 변경안에 따라 순차적으로 협의할 수 있습니다.

## 1 질문 6개에 대한 답변

| 질문 | 서버 측 답변 |
| --- | --- |
| Q1 ProgramStop의 의미 | 기존에 확정한 의미는 **컨베이어·로봇팔 정지 요청**입니다. 서버 프로그램과 WebSocket 연결은 유지합니다. HMI 화면 종료나 별도의 종료 정리 절차까지 뜻하지 않습니다. 따라서 수신 Reply만 받고 5초 뒤 장비 정지가 완료된 것으로 간주해서는 안 됩니다. 일반 정지 버튼용 `Stop`은 `ProgramStop`과 같은 장비 정지 요청의 별칭으로 추가하는 안을 제안합니다. 작업을 마친 뒤 정지할지 즉시 정지할지는 장비 제어 규약과 별도 확정해야 합니다. |
| Q2 Home의 의미 | **원점 복귀**가 맞습니다. 기존 README의 버튼 이름을 ‘원점 복귀’로 수정했습니다. 현재 자세를 저장하는 HMI의 ‘원점 잡기’와 구분합니다. |
| Q3 HMI가 원점을 저장하고 Home에 각도를 전송 | 제안한 `Home/Motors` 구조의 수신·검증을 추가했습니다. 정상 각도 데이터에는 수신 확인만 돌려주며 실제 복귀나 서버 측 저장은 하지 않습니다. 실제 이동은 장비 규약 확인 후 연결해야 합니다. |
| Q4 6번 모터도 deg인지 | **현행 XML에서는 1~6번 모두 `unit="deg"`입니다.** 다만 실제 하드웨어에서 6번이 그리퍼인지, 그리퍼 값이 회전 각도인지 개폐량인지, 변환 범위는 무엇인지 아직 검증하지 않았습니다. 현재 화면 해석은 deg를 유지하되 실제 장비 적용 전 모터 대응표와 단위를 확인해야 합니다. |
| Q5 자동 작업이 원점을 사용하는지 | 현재 서버에는 자동 공정 제어가 없어 확정할 수 없습니다. ‘사용하지 않는다’고 확답할 단계가 아닙니다. 자동 시작·종료 때 원점이 필요한지 장비 담당과 정한 뒤, 필요하면 `ProgramStart`의 원점 전달 또는 다른 원점 공유 방식을 함께 정해야 합니다. |
| Q6 서버 주소 | 현재 코드의 기본 주소는 `ws://127.0.0.1:5080/ws/hmi`이며 같은 PC에서만 접속됩니다. 다른 장비에서는 `ws://서버내부IP:5080/ws/hmi`, 포트포워딩한 외부에서는 `ws://공인IP:외부포트/ws/hmi` 형식입니다. 서버 PC의 실제 주소와 공유기 외부 포트는 별도 전달하겠습니다. **실제 접속 주소는 아직 이 회신에 확정되어 있지 않습니다.** |

`localhost`는 HMI가 실행되는 PC 자신을 뜻합니다. 서버와 HMI가 다른 PC라면 HMI 기본값을 실제 서버 주소로 바꿔야 합니다. 문서의 주소 표기는 형식 예시이며 그대로 연결하는 주소가 아닙니다.

## 2 현재 구현과 맞춰야 할 HMI 처리

### 수신 확인과 완료 표시

현재 정상 명령 응답은 `result="Received" code="ReceiptOnly" executed="false"`입니다. 실제 동작을 실행하거나 대기열에 저장하지 않습니다. 시뮬레이션도 현재는 가상 상태만 주기적으로 만들며 명령에 따라 상태를 바꾸지는 않습니다.

따라서 현재 `ProgramStop` Reply 뒤 5초가 지났다는 이유만으로 ‘장비 정지 완료’나 ‘안전하게 종료됨’을 표시하지 않도록 조정 부탁드립니다. 실제 정지 확인까지는 상태 화면을 유지하고 미확인 상태를 표시하는 안을 제안합니다. HMI 화면 자체의 종료와 장비 정지 완료는 별개로 취급해야 합니다.

### 거절 응답의 요청 대응

HMI 문서에는 Reply를 id·명령명·목표 모드가 모두 맞을 때만 처리한다고 되어 있습니다. 현재 서버의 `SetMode` 거절 Reply에는 `mode`가 없고, 명령 구조가 잘못되면 `command`도 생략될 수 있습니다.

거절 응답은 먼저 `id`로 요청을 찾고, 존재하는 속성만 대조하는 처리를 제안합니다. 정상 응답은 명령명과 목표 모드를 계속 확인해도 됩니다. `Error`에 유효한 id가 없으면 특정 버튼 요청을 임의로 완료 처리하지 않습니다. 이 차이를 그대로 두면 서버가 거절했는데도 HMI에는 ‘응답 미확인’으로 보일 수 있습니다.

### 명령별 현재 응답

| 요청 | 현재 서버 응답 |
| --- | --- |
| `Home`에 유효한 `Motors` 포함 | `Reply / Received / ReceiptOnly`, `executed=false` |
| `Home/Motors`의 모터 중복·누락, 잘못된 각도·단위 | `Reply / Rejected / InvalidAngles` |
| `Stop` | `Reply / Rejected / UnknownCommand` |
| `EmergencyStopRelease` | `Reply / Received / ReceiptOnly`, `executed=false` |
| `CameraStart` 또는 `CameraStop`에 `camera` 속성 포함 | `Reply / Rejected / InvalidCommand` |
| `CameraStart` 또는 `CameraStop`에 `camera` 속성 없음 | `Reply / Rejected / UnknownCommand` |

카메라 명령은 현재 속성 검사가 명령명 검사보다 먼저이므로 HMI 문서의 응답 표와 일부 차이가 있습니다.

## 3 1순위 요청 검토

| 요청 항목 | 현재 상태 | 변경 가능 여부와 협의 조건 |
| --- | --- | --- |
| 2.1 `Line` | 미구현 | 제안하신 요소와 상태값으로 구현 가능합니다. 우선 시뮬레이션 상태 전이를 만들고, 실제 모드·긴급정지·동작 상태는 장비 피드백에 연결하는 안입니다. 실장비 상태를 모르는 동안 `Stopped`나 `emergencyStop="false"`를 실제 확인값처럼 보내지 않겠습니다. |
| 2.2 `Home/Motors` | 수신·형식 검증 구현 | 모터 1~6의 중복·누락, deg 단위, 유한한 숫자인지 검증합니다. 실제 이동과 장비별 허용 범위 검증은 장비 연동 단계에 남아 있습니다. |
| 2.3 `EmergencyStopRelease` | 수신 확인 구현 | 현재는 실제·가상 상태를 바꾸지 않습니다. 실제 긴급정지 해제는 하드웨어의 해제 조건과 확인 신호가 필요합니다. 해제 후 자동 재가동하지 않고 정지를 유지하는 방향에 동의합니다. |
| 2.4 실행 결과와 거절 사유 | 수신 확인과 형식 오류만 지원 | 제안한 코드와 `Param` 구조로 확장 가능합니다. 장비 명령 발행·수락·완료의 경계를 아래와 같이 먼저 맞춰야 합니다. |
| 2.5 완료 이벤트 | 미구현 | `HomeCompleted`는 실제 복귀 완료 확인 뒤 보낼 수 있습니다. `ShutdownCompleted`는 현재 종료 절차가 없으므로 바로 추가하기보다 Q1의 의미부터 합의해야 합니다. 현행 장비 정지 의미에는 `LineStopped`가 맞습니다. |
| 2.6 변경 직후 전체 HMI에 전송 | 각 연결에 주기 상태 전송만 있음 | 공유 상태가 바뀌면 접속한 모든 HMI에 상태·이벤트를 보내는 기능을 추가할 수 있습니다. 1초 주기 전송은 유지하고 Reply는 요청한 연결에만 보내겠습니다. 시뮬레이션부터 검증할 수 있습니다. |

### Line과 운전 조건

정지 상태에서만 모드 전환, 자동·정지 상태에서 원점 복귀, 긴급정지 해제 후 정지 유지, 자동 모드에서 `homeRequired`일 때 시작 거절이라는 규칙은 서버에도 구현 가능합니다. 아직 실제로 적용된 규칙은 아닙니다.

다만 **수동 모드가 원점 복귀 요구만 면제하는지**와 **수동 시작 때 컨베이어·카메라도 가동하는지**는 확인이 필요합니다. 수동이라고 긴급정지, 고장, 필수 장치 연결 검사를 함께 면제하지 않는 방향을 제안합니다.

장비 연결 전에는 `source="unavailable"` 상태에서 `Line`을 생략하여 HMI가 ‘상태 미수신’을 유지하는 안을 제안합니다. 시뮬레이션에서만 `source="simulation"`과 가상 `Line`을 제공합니다. 실제 운전 상태를 제공하려면 실제 데이터임을 나타내는 `source` 값과 상태의 유효성도 추가 합의가 필요합니다.

### 원점 각도 검증과 저장

원점 각도 수신 시 앞의 세 조건을 검사합니다. 마지막 장비별 조건은 실제 제어 전에 추가할 사항입니다.

- `Motor/@id` 1~6이 각각 한 번씩 있어야 합니다. 요소 순서가 아니라 id로 매칭합니다.
- 각 모터에 Angle 하나가 있어야 하며 값은 유한한 숫자여야 합니다. `NaN`, 무한대, 빈 값은 거절합니다.
- 현재 규약에서는 `unit="deg"`만 허용합니다. 다른 단위는 변환 규약 합의 전 거절합니다.
- 실제 이동 전에는 모터별 최소·최대 각도, 영점, 방향, 그리퍼 대응을 장비 설정으로 검증해야 합니다. 임의의 공통 각도 범위를 확정하지 않습니다.

HMI는 최신의 `valid="true"`인 값만 원점으로 저장해야 합니다. 리더암 각도와 팔로워의 실제 각도가 항상 일치한다고 볼 수 없으므로, 실제 원점 복귀에는 팔로워 값 또는 검증된 리더암→팔로워 변환이 필요합니다.

저장 없이 각도를 전달하는 방식을 채택하면 여러 HMI가 서로 다른 원점을 가질 수 있습니다. 원점 저장·복귀 명령을 어느 화면에서 허용할지 함께 정해 주세요.

현재 각도 없는 `Home`도 수신 확인만 받습니다. 1차 호환성 확장에서는 이 동작을 유지하고, 실제 실행 단계에서 원점이 없는 요청은 제안하신 `HomeNotSet`으로 거절하는 안입니다. 필수화 시점은 HMI와 맞추겠습니다.

### 실행 시작과 완료의 구분

| 단계 | 응답 또는 알림 제안 | 의미 |
| --- | --- | --- |
| 통신 검증만 수행 | 기존 `Received / ReceiptOnly / executed=false` | 정상 수신했지만 실행·예약하지 않음 |
| 실행 조건 충족, 장비 제어 계층에서 요청 수락 확인 | 제안하신 `Received / Accepted / executed=true` | 실행 요청이 수락되어 시작 절차에 들어감. 최종 동작 완료는 아님 |
| 실행 불가 | `Rejected / 거절 코드 / executed=false` | 조건 불충족 또는 형식 오류 |
| 동작 완료 | `HomeCompleted`, `LineStopped` 등의 Event와 최신 Status | 장비 피드백으로 완료 확인 |

`executed=true`를 ‘장비 동작 완료’로 해석하지 않는다는 합의가 필요합니다. 네트워크로 명령을 썼다는 사실만으로 이 값을 true로 만들지 않는 방향을 제안합니다. 장비 수락 확인 자체가 없거나 불명확한 경우에는 실행 성공을 확정할 수 없습니다.

시뮬레이션은 실장비와 혼동되지 않도록 표시가 필요합니다. 상태의 `source="simulation"` 외에도 Reply/Event에 시뮬레이션 표시를 추가할지, HMI가 연결 상태의 source를 기준으로 해석할지 협의 부탁드립니다. 그 전에는 가상 성공을 실제 실행 성공처럼 표시하지 않습니다.

긴급정지·정지 요청은 장치 일부가 끊겼다는 이유만으로 모든 정지 시도를 포기하지 않도록 장비 제어 단계에서 설계해야 합니다. 일부 장치만 정지했거나 완료 확인을 받지 못한 경우의 표현은 별도 합의가 필요합니다.

### 이벤트와 다중 화면

Event의 `code`, `level`, `Param`, `seq` 구조는 사용 가능합니다. `seq`는 서버 재시작 시 초기화되므로 재시작을 넘어 유일한 식별자로 간주하지 않도록 해야 합니다.

완료 이벤트는 모든 HMI에 방송되므로 원 요청을 알아볼 수 있게 `Param name="requestId"`를 추가하는 안을 제안합니다. HMI가 이를 읽도록 수정할 수 있는지 확인 부탁드립니다. 특히 한 화면의 요청 완료로 다른 화면까지 자동 종료시키지 않아야 합니다.

상태 변경 직후 전송을 추가해도 인터넷 경유 통신의 즉시 도착을 보장하지는 못합니다. 재접속 시에는 최신 Status로 복구하고, 누락된 이벤트의 재전송·영구 기록은 별도 기능으로 구분하겠습니다.

## 4 2순위와 3순위 요청 검토

| 요청 항목 | 검토 결과 |
| --- | --- |
| 3.1 `Fault` | 구조 추가는 가능합니다. 실제 고장 코드, 임계값, 해제 조건은 장비 담당 확인이 필요합니다. `Start`를 누른 사실만으로 남아 있는 고장을 지우지는 않아야 합니다. 장비 상태가 유효하지 않은 동안 Fault 부재를 ‘고장 없음’으로 해석하지 않도록 협의가 필요합니다. 동시 고장 여러 건의 표현도 정해야 합니다. |
| 3.2 `Event` | 상태 전이·완료 알림에 필요하므로 핵심 이벤트는 1순위 상태 기능과 함께 구현하는 안입니다. 고장·부품 판정 등 실데이터 이벤트는 해당 공급원 연결 후 추가합니다. |
| 3.3 `LeaderArm`, `Camera` 연결 | XML 확장은 가능합니다. 실제 연결 여부를 공급할 인터페이스가 필요합니다. 카메라 `top`, `close`는 후보 이름으로 사용할 수 있으나 실제 카메라 수와 대응은 아직 확정되지 않았습니다. |
| 3.4 일반 정지 `Stop` | 1차로 `ProgramStop`과 같은 정지 요청의 별칭을 제안합니다. 별도의 프로그램 종료 시퀀스를 도입하려면 명령 의미와 완료 이벤트를 다시 합의해야 합니다. |
| 3.5 카메라 제어와 영상 | 명령·URL 메타데이터 구조는 수용 가능합니다. 실제 영상 공급원과 카메라 제어 권한이 필요하며, MJPEG 제공 가능 여부와 대역폭을 확인한 뒤 전송 방식을 결정해야 합니다. `camera` 생략 시 전체 카메라 처리, 잘못된 id, 일부 실패 규칙도 합의가 필요합니다. |
| 4.1 개별 `Inspection` | 현재 Status의 누적 개수는 유지하고 별도 메시지를 추가하는 구조가 가능합니다. 실제 판정 공급원 연결이 필요합니다. 부품 id의 유일 범위, 중복 판정, 카운터 초기화·재시작 기준을 먼저 정해야 합니다. |
| 4.2 `Cycle` | 제안한 상태 구조는 사용 가능합니다. 실제 단계는 공정 제어 프로그램이 보고해야 하며 서버가 시간만으로 추측해서 표시하지 않는 방향입니다. |
| 4.3 팔로워 각도 | 기존 리더암 `Motors`를 유지하면서 `Motors role="follower"`를 추가할 수 있습니다. HMI는 두 요소를 역할로 구분해야 합니다. 실제 각도와 각 모터의 `valid`는 장비 데이터에 연결해야 합니다. |
| 4.4 서보 온도·전압·부하 | 사용 중인 서보와 로봇 컴퓨터 API가 값을 제공하는지 확인이 필요합니다. 가능하면 모터별 값·단위·유효성을 함께 보내는 안입니다. 온도는 °C, 전압은 V를 후보로 하고, ‘부하’는 전류·토크·백분율 중 실제 의미를 확인한 뒤 규약을 정해야 합니다. |

포트포워딩 환경에서는 카메라 URL도 HMI가 실제로 접근 가능한 주소여야 합니다. 내부 IP가 들어간 영상 주소는 외부 HMI에서 사용할 수 없습니다. 상대 경로는 접속 주소의 호스트와 외부 포트를 유지하고, `ws→http`, `wss→https` 대응을 적용하는 방향을 제안합니다.

## 5 HMI 및 장비 담당에게 확인을 부탁드리는 내용

1. `ProgramStop`을 장비 정지로 유지하고 `Stop`을 별칭으로 추가하는 안이 가능한지 확인 부탁드립니다. 종료 화면이 꼭 필요하면 장비 정지 완료 확인과 화면 종료의 연결 규칙을 별도로 정하고 싶습니다.
2. 5초 뒤 종료 화면 전환과 거절 Reply의 mode 필수 매칭을 위 설명에 맞게 조정할 수 있는지 확인 부탁드립니다.
3. 수동 모드에서 시작할 때 실제 가동할 장치와 자동 작업에서 원점을 사용하는지 알려 주세요.
4. 1~6번 모터 대응, 그리퍼 단위, 각도 범위·영점·방향, 팔로워 현재각 제공 여부를 확인 부탁드립니다.
5. 실제 HMI 파일과 `tools/server-check.html`을 전달해 주세요. 현재 확인한 자료는 요청 문서이며, 실제 HMI와 서버의 통합 검사는 아직 하지 않았습니다.
6. HMI를 HTTPS로 제공하는지 확인 부탁드립니다. HTTPS 화면에서 접속하려면 WSS 구성이 필요할 수 있으며, 현재 서버는 TLS·접속 인증을 구성하지 않았습니다. 실제 외부 주소와 함께 접속 방식을 확정해야 합니다.

통신 단절 시 DC 전원 케이블을 뽑도록 안내하는 문구와 화면 긴급정지만 사용하는 구성은 하드웨어 담당의 검토가 필요합니다. 전원 차단 시 팔의 낙하·잔류 동작 등 장비별 조건이 다르므로 이 회신으로 그 절차를 승인하지는 않습니다. 하드웨어 안전 정지와 소프트웨어 상태 표시는 분리해 확인해야 합니다.

## 6 서버 측 변경 제안과 진행 순서

아래에서 반영 완료한 항목 외에는 협의·승인 후 진행할 범위입니다. 확장 메시지 이름은 가급적 요청서와 맞추되 기존 필드의 의미 변경은 별도 합의하겠습니다. 이번 수신 확장은 `version="1.0"`을 유지합니다. 필수값이나 기존 명령 의미를 바꾸는 경우 버전·전환 시점을 다시 협의합니다.

### 1차 명령 수신 호환성

- 반영 완료: `Home`에만 제안된 `Motors` 본문을 허용하고 6개 각도·id·단위를 검증합니다.
- 반영 완료: `EmergencyStopRelease`를 신규 수신 명령으로 추가했습니다.
- 제안 유지: `Stop`을 장비 정지 요청의 별칭으로 추가하는 것은 이번 수정 범위에 포함하지 않았습니다.
- 이 단계의 정상 Reply는 `ReceiptOnly / executed=false`를 유지하고 실제 동작이나 상태 전이는 하지 않습니다.
- 반영 완료: README의 Home 버튼 표기, 신규 명령·오류 예제, 통신 검사를 업데이트했습니다.

### 2차 상태와 시뮬레이션

- 공유 `Line` 상태와 운전 조건 검증, 긴급정지·해제·원점 복귀의 시뮬레이션을 추가합니다.
- 상태에 따른 거절 코드와 `Param`, 핵심 Event, 상태 변경 즉시 전체 HMI 전송을 추가합니다.
- HMI 3개 동시 접속에서 요청자별 Reply, 공통 상태 일치, 정지·해제·원점 복귀, 재접속 복구를 확인합니다.

### 3차 실제 장비 연결

- 로봇·컨베이어·검사·카메라의 실제 통신 규약에 연결합니다.
- 장비 피드백을 근거로 실제 상태, 실행 수락, 완료, 고장을 보고합니다.
- 실행 명령 중복 방지, 여러 HMI의 상충 명령 처리, 통신 단절 시 장비 동작을 검증합니다.

Home 각도와 긴급정지 해제의 수신 확장은 반영했으며 Stop 별칭은 제안 단계입니다. 2차는 위 상태·완료 의미를 합의하면 시뮬레이션부터 진행할 수 있으며, 3차는 장비 인터페이스와 안전 조건 확인이 선행되어야 합니다.
